# Desktop startup repair — 13 October 2026

## Windows PowerShell follow-up

The user's captured log showed all deployments ready, followed by a fatal `NoProxy` parameter error. Windows PowerShell 5.1 does not support that parameter. The script therefore exited before establishing browser port forwarding. The same error was swallowed by authentication retries, adding delay and falsely reporting that Keycloak was still starting. Startup and auth configuration now share version-compatible HTTP options with basic parsing.

Browser forwarding now runs before the best-effort Prometheus reload. Ordinary starts no longer restart all seven application deployments: configuration checksums restart only changed workloads, while `-ImportImages` still forces updates for rebuilt images. MongoDB keeps its memory limit and sparse steady-state checks, but has a one-core CPU ceiling, a 20-second health timeout and 5-second startup checks. Previously its 10-second timeout and 60-second interval could miss readiness repeatedly under cold-start contention. Infrastructure starts before monitoring to reduce that contention. No data volumes are removed.

Validated by invoking `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/start.ps1` (Windows PowerShell 5.1): startup completed with exit code zero and checked the web page plus all five service health routes. MongoDB's first health check succeeded about 19 seconds after container start, compared with the roughly 198-second dependency wait in the submitted log. This is a local observation; a full Docker/Windows cold boot can take longer. Installing the configuration-checksum annotations causes one initial rollout; subsequent unchanged starts reuse the pods.

Local forwarding now binds both loopback address families (`--address localhost`). IPv4-only binding caused approximately two-second IPv6 fallback delays for `localhost` requests. Final probes returned web HTTP 200 in 316 ms, finance health in 37 ms and gateway notification health in 36 ms. Windows PowerShell array serialization of the forward registry was also corrected; stale forwards are replaced only after verifying their executable, cluster context, namespace and service command line. All eight pods were ready with zero restarts after the repair.

The running desktop had both Compose application containers and Kubernetes application pods, plus the full ELK/Tempo/CDC stack. Kubernetes database EndpointSlices still referenced addresses assigned before Docker restarted. The finance pod repeatedly failed startup with `Connection to postgres:5432 refused`; capture, analytics and rates were also unready. This caused resource contention and failed account loading rather than an expensive financial calculation in the UI.

Run `./scripts/start.ps1` after Docker Desktop and its Kubernetes cluster are ready, then open http://localhost:30080. The script selects daily mode, stops duplicate Compose app containers and heavy observability tools, refreshes infrastructure addresses, deploys the Kubernetes services, restores browser forwarding, and checks service readiness. Existing data volumes and application features remain intact. Full observability is available with `-Profile full`; rebuilt images or a reset cluster require `-ImportImages`.

The Kubernetes startup path now calls `runtime-profile.ps1 -InfrastructureOnly`, avoiding the previous sequence of scaling down Kubernetes, starting all Compose app services, and immediately stopping them again to redeploy Kubernetes. Normal startup also skips unnecessary image exports/imports. Docker Desktop's Compose group Start All does not perform these orchestration steps and should not be used as the application launcher.

Validation after recovery: all eight Kubernetes pods ready; fixture sign-ins measured 1,276 ms and 347 ms; initial authenticated workbench load 1,273 ms; workbench save 557 ms through the browser endpoint. These are local fixture measurements, not load-test guarantees. Account save/reload, idempotent replay, two-user isolation, stale revision rejection, invalid-data rejection and anonymous access rejection passed. The test restores fixture finance data. No user financial records were edited.
