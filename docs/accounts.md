# Account-owned workbench

The welcome page offers sign-in and registration. Keycloak owns credentials, registration email verification, reset links and profile updates; the Ledgerline theme covers those forms. Authorization uses code flow with PKCE S256. Tokens stay in tab session storage, not finance documents or exported files. A signed-out visitor cannot open financial screens. Account settings provide password/profile management and identity-provider logout.

The Java service exposes `GET/PUT /api/v1/core/me/workbench` and `GET /api/v1/core/me/history`. The owner is taken exclusively from the validated token subject. Clients cannot select another owner by workspace ID, query parameter or JSON property. PostgreSQL stores two private workspaces per subject. New users get empty activity, commitments and budgets, and zero opening balances. Old browser sample data is not silently imported.

A workbench contains transactions, financial-account opening balances, commitments, category budgets and workspace names. A PUT has the expected revision, a UUID request ID and both workspaces. The service validates dates, decimal amounts, unique IDs, account references, payment links and collection bounds, then locks the owner's row. Updating the document, recording the prior revision and inserting the outbox event happen in one database transaction. A stale revision returns 409; the page offers refresh rather than merging or overwriting automatically. An identical request replay at the latest revision does not write twice.

The UI waits for the server response before applying a change or reporting success. A failed response retains the previous confirmed view and leaves entry fields available. Concurrent editing in another tab requires an explicit refresh. Opening the app on a different browser/device reads the same account data. Theme preference is a small local value scoped by subject; financial data is not written to local storage.

Financial accounts support creation, renaming and signed opening balances. Renaming changes transaction account references atomically. Accounts used by transactions cannot be removed, and `Main account` remains available for linked bill payments. Expenses, income and same-currency transfers use decimal arithmetic. Transactions can be corrected or deleted from the tracker, with earlier snapshots retained in history. Linked payment amounts cannot be edited from the UI and linked payment transactions cannot be deleted. The separate accounting journal is immutable and is not the workbench document.

Bills/subscriptions support amount, due date, category, cadence, cancellation/reopening and once-only linked payment recording. A paid recurring item offers **Track next cycle**, retaining the previous payment and creating an open next occurrence. Month/year advancement preserves the billing-day anchor while clamping short months, so January 31 advances to February 28 and then March 31; leap-day yearly schedules return to February 29 in a leap year. Duplicate next cycles are rejected in the UI. Cycle creation is an explicit action, not an automatic server scheduler. Category budgets recur monthly; spending reflects the selected month's expenses. CSV activity and full-account JSON exports are available.

Confirmed commitments sync to Node/Cassandra under the same token subject. The sync checks its expected owner to avoid moving a previous user's snapshot to a new session. Verification, scheduled SMTP delivery and inbox history remain private to the account. Sync currently requires an open browser; server-driven finance event consumption remains phase work.

Bounded workspaces currently support INR, 30 financial accounts, 10,000 transactions, 100 active commitments plus up to 1,000 total cycles and 50 budget limits per workspace, with a 2 MB document bound. Revision history keeps prior finance documents for audit; production retention and account-erasure policy must be implemented before a public launch. Shared business membership, multi-currency, bank connections, receipt/import APIs and regulatory accounting exports are not implied by private business workspaces.


Overall budgets use the reserved `All spending` budget scope. They count expenses across every category in the reporting month, excluding income/transfers. Independent category limits remain available underneath the overall plan and are never added to it. Without an overall budget, the summary shows the sum of category limits with that label.

Recording a payment now asks for its account and date. Recurring commitments can create the next unpaid cycle in the same atomic save, preserving the prior linked payment and the original billing-day anchor. Repeated saves cannot pay the same open cycle twice. Only active commitments are projected to the reminder service, keeping historical cycles out of the scheduler.
